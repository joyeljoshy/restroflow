# Security model

## Trust boundaries

Untrusted inputs include browser JSON, route/query parameters, cookies, Socket.IO handshakes/events, raw image uploads, headers, and environment variables. Zod validates HTTP and event boundaries; production environment parsing fails fast. PostgreSQL constraints remain a final invariant backstop.

## Staff authentication

- Passwords are Argon2id hashes. Unknown-account login still performs a dummy verification to reduce account enumeration timing differences.
- Login creates a cryptographically random opaque token; only its SHA-256 hash is stored.
- The cookie is HTTP-only, path `/`, time-bounded, and `Secure` in production.
- Local same-site development uses `SameSite=Lax`. The provider-domain deployment explicitly uses `SameSite=None; Secure` because Vercel and Render are cross-site.
- Logout revokes the server-side session. Expired/revoked sessions, inactive users, and users without active memberships are rejected.
- Changing a staff role or activation state revokes active sessions. The last active admin cannot be demoted or deactivated.

`SameSite=None` does not override browser third-party-cookie blocking. The generated provider-domain architecture therefore requires Chrome, Firefox, and Safari acceptance testing. If target browsers block the cookies, the preferred long-term fix is same-site custom domains; Vercel cannot proxy the persistent Render WebSocket through a serverless Next.js function reliably.

## Customer authentication

A QR identifier locates a table but grants no ordering permission. Staff issue a six-digit activation code that is cryptographically generated, Argon2id-hashed, one-time, expires after ten minutes, and locks after five failures. Successful activation creates a separate four-hour opaque customer session bound to the restaurant and open table session. Customers can read/subscribe only to orders created by their session.

The short staff-mediated code is MVP proof of access, not strong proof of physical presence. Relay remains possible; expiration, attempt limits, replacement, and source limits reduce rather than eliminate that risk.

## Authorization and isolation

Protected staff requests perform authentication, restaurant membership selection, and role checks before reaching controllers. Services enforce ownership and transition policies. Repositories include the verified restaurant identifier in reads and writes. Customer and staff permissions never share middleware or token names.

Socket handshakes read the matching HTTP-only cookie, derive restaurant/customer scope server-side, and allow only exact configured origins. Staff room access is role-based; customer subscriptions verify order ownership. Sessions/roles are revalidated periodically, on subscription, and before publication where relevant.

## Browser request protection

- CORS uses exact `CORS_ORIGINS` values and credentials; wildcard origins are not allowed.
- Browser mutation requests with an `Origin` header must match the same allowlist.
- Non-browser clients may omit `Origin` but still require authentication and authorization.
- Socket.IO applies the same exact-origin policy in CORS and `allowRequest`.
- JSON bodies are limited to 1 MB; image bodies to 3 MB.
- Render proxy trust is a bounded hop count (`TRUST_PROXY_HOPS=1`), not a blanket trust setting, so source-based rate limits use the intended client address.

## Images

Both local and Cloudinary adapters enforce JPEG/PNG/WebP content types, 1 byte–3 MB size, and file-signature checks before writing or uploading. Names/public IDs are UUIDs generated by the server. Production performs a signed SDK upload using backend-only credentials and accepts only an HTTPS delivery URL under the configured Cloudinary cloud. There are no unsigned browser uploads.

Images are not automatically deleted when menu records change. That preserves historical references and avoids destructive cleanup; an operator should periodically review orphaned Cloudinary assets and delete only after explicit confirmation.

## Platform controls

Express disables `x-powered-by`, applies Helmet, emits request IDs, and returns centralized typed public errors. Pino redacts cookie and authorization headers. Secrets, password values, tokens, activation codes, database URLs, and Cloudinary API secrets must remain provider environment variables.

Liveness does not query PostgreSQL. Readiness performs a safe database check and returns a sanitized degraded response. Startup errors and shutdown signals are logged without exposing credentials; Socket.IO and Prisma are closed during graceful shutdown.

## Dependency risk

The Part 11 audit found one Effect `Schema.TemplateLiteral` ReDoS advisory reported through three dependency-chain entries (`prisma -> @prisma/config -> effect`). RestroFlow does not import the affected API, but Prisma operational tooling loads the dependency, so reachability is reduced, not zero. The correct action is to upgrade aligned Prisma packages once a compatible stable release carries a fixed Effect version, then rerun generation, schema validation, migration status, compiled startup, and the complete suite. A forced Prisma 6 downgrade or `npm audit fix --force` is not accepted.

## Production acceptance checklist

- Verify `Secure; HttpOnly; SameSite=None` on both cookie types in a real browser.
- Verify trusted and untrusted REST origins and Socket.IO handshakes.
- Exercise role revocation, expiration, cross-role denial, cross-restaurant denial, and cross-customer denial.
- Confirm secrets and raw cookies never appear in Render logs.
- Confirm HTTPS/WSS only and no mixed content.
- Confirm rate-limit IP behavior behind Render.
- Review tax/legal behavior and conduct manual assistive-technology testing before real use.
